# Сервис учёта материалов для творчества 🎨

У каждого, кто рисует, вяжет или шьёт, рано или поздно появляется «тот самый ящик»: там лежит полтюбика акварели, три мотка одинаковой пряжи и бисер, про который все забыли. А потом садишься работать и выясняется, что нужной краски как раз нет.

Эта программа помогает навести порядок. Она помнит, что у вас есть и сколько, записывает, кто что взял или докупил, и сама напоминает, когда что-то пора пополнить.

Раньше с ней можно было работать только в консоли. Теперь у неё есть веб-версия, а данные сайта хранятся в SQLite и доступны через Django ORM: материалы, историю операций и статистику можно смотреть прямо в браузере.

## Кому пригодится

Всем, у кого дома или в мастерской копятся материалы для творчества: художникам и иллюстраторам, тем, кто шьёт, вяжет и плетёт из бисера, студентам творческих специальностей, небольшим мастерским и кружкам, где одними материалами пользуются несколько человек.

## Что можно делать

**В браузере:**

- посмотреть все материалы карточками: что заканчивается, сразу подсвечено красным, а сверху видно, сколько всего позиций;
- открыть карточку материала и увидеть его категорию, остаток, дату добавления и всю историю: кто и когда его брал или докупал;
- найти материалы по названию, категории и остатку, например «все краски, которых осталось 3 штуки и меньше»;
- посмотреть историю всех операций, отдельно только активные или только отменённые, и открыть любую из них подробно, вместе с материалом и человеком, который её сделал; искать операции по материалу или пользователю, фильтровать по дате, материалу и пользователю, выбирать сортировку и переходить между страницами по 5 записей;
- открыть статистику: сколько всего материалов и единиц, что по категориям, что заканчивается, кто чаще всего пользуется материалами.

**В консоли** (всё, что было раньше, работает):

- добавлять, искать, сортировать и удалять материалы;
- записывать расход и пополнение, отменять ошибочные операции;
- добавлять и искать пользователей;
- смотреть статистику.

Добавление и изменение через административную панель доступны по `/admin/`. В ПР11 добавлены пользовательские формы операций: создание, редактирование активной записи и отмена. Консольная версия продолжает работать с JSON отдельно от сайта.

## Страницы сайта

| Адрес | Что там | Имя маршрута |
|---|---|---|
| `/` | главная: пара слов о сервисе и кнопки в разделы | `homepage:index` |
| `/materials/` | все материалы карточками | `materials:list` |
| `/materials/search/` | поиск по категории и остатку | `materials:search` |
| `/materials/<slug>/` | один материал и его история | `materials:detail` |
| `/materials/<id>/` | перенаправление на новый адрес | `materials:legacy_detail` |
| `/operations/` | история операций; `?status=active` или `?status=cancelled` — только активные или отменённые | `operations:list` |
| `/operations/<id>/` | подробности одной операции | `operations:detail` |
| `/statistics/` | итоги, группировки, что заканчивается, статистика статусов | `homepage:statistics` |
| `/admin/` | управление материалами, участниками и операциями | встроенная Django Admin |

Если открыть материал или операцию, которых нет (например, `/materials/9999/`), сайт честно скажет «не найдено» и вернёт код 404. А для совсем несуществующих адресов есть своя аккуратная страница 404 с кнопкой «На главную» (её видно, когда в настройках выключен режим отладки).

## Как это устроено

Когда вы открываете страницу, браузер отправляет запрос. Django смотрит на адрес, находит подходящий маршрут и вызывает нужную функцию. Дальше работа делится на две части:

- **функция (view)** только готовит данные: выполняет запрос через модели Django ORM, получает объекты или словари и складывает их в «контекст» — обычный словарь вроде `{"materials": materials_list}`;
- **шаблон** — отдельный HTML-файл — берёт эти данные и превращает их в страницу. Для этого в нём есть язык шаблонов Django: `{{ material.name }}` выводит значение, `{% for %}` перебирает список, `{% if %}` показывает разное в разных ситуациях.

Связывает их функция `render()`: она берёт запрос, имя шаблона и контекст и возвращает готовую страницу. HTML внутри Python-кода больше нет, старая функция `page()` из прошлой версии удалена.

### Один каркас на все страницы

Шапка с логотипом и меню, подключение стилей, подвал и скрипт описаны один раз, в базовом шаблоне `templates/base.html`. В нём оставлены «окошки» — блоки `{% block title %}` (заголовок вкладки) и `{% block content %}` (середина страницы). Каждая страница начинается со строки `{% extends "base.html" %}` и заполняет только эти окошки. Поэтому, если поменять меню, оно поменяется сразу везде.

### Повторяющиеся кусочки

То, что встречается в нескольких местах, вынесено в маленькие шаблоны и подключается через `{% include %}`:

- меню сайта — `includes/navigation.html`;
- карточка материала — `materials/includes/material_card.html` (её повторяет цикл на странице материалов);
- метка остатка «9 шт.» или «1 шт. · заканчивается» — `materials/includes/stock_badge.html`, она одинаковая в карточке и на странице материала;
- метка статуса операции «Активна» или «Отменена» — `operations/includes/operation_status.html`, её используют история операций, страница операции и история на странице материала.

### Если показывать нечего

Пустые списки обрабатываются прямо в шаблоне через `{% empty %}`: если материалов нет, будет «Материалы не найдены.», если у материала ещё не было операций — так и будет написано. А если материал или операция не найдены, шаблон через `{% if %}` покажет сообщение «не найдено», и ответ придёт с кодом 404.

### Ссылки по именам

В шаблонах нет адресов, написанных вручную. У каждого раздела есть своё пространство имён (`app_name` в `urls.py`), у каждого маршрута — имя, и ссылки строятся так: `{% url 'materials:detail' material.id %}`. Если когда-нибудь адрес раздела поменяется, ссылки перестроятся сами.

### Фильтры

Фильтры немного меняют то, как значение выглядит на странице, не трогая сами данные:

- `{{ materials|length }}` — сколько всего материалов или операций;
- `{{ material.name|default:"Без названия" }}` — подстраховка, если название пустое;
- `{{ operation.amount|stringformat:"+d" }}` — количество со знаком: «+4» для пополнения и «-2» для расхода.

В ORM даты описаны полями DateField. На страницах они выводятся фильтром date:"Y-m-d", сохраняя прежний вид.

### Свои стили, картинка и скрипт

Оформление по-прежнему опирается на Bootstrap 5.3, но у проекта теперь есть и свой внешний вид. Файлы лежат в `homepage/static/homepage/` и подключаются через `{% load static %}` и `{% static '...' %}`:

- `css/style.css` — тёплый «бумажный» фон, терракотовые акценты, карточки материалов с цветной полоской слева, зачёркнутый статус у отменённых операций;
- `img/logo.png` — логотип-палитра в шапке;
- `js/main.js` — небольшой скрипт, который сам ставит текущий год в подвале.

### Что внутри

Программа думает о мире в трёх понятиях. В базе данных это три таблицы, а в консольной версии — три Python-класса:

- **Материал** (`Material`) — то, что лежит на полке: название, категория, количество, дата добавления. Сам следит, чтобы его количество не ушло в минус, и знает, когда заканчивается.
- **Пользователь** (`User`) — человек, который берёт или докупает материалы: имя и почта.
- **Операция** (`Operation`) — запись о том, что кто-то взял или добавил материал. Хранит сам материал и самого пользователя, поэтому на странице операции сразу видно и то и другое. Её можно отменить: количество вернётся, а запись останется в истории.

## Где хранятся данные

После ПР9 **сайт работает через Django ORM с `db.sqlite3`**, указанной в
`craftbox/settings.py`. Структурой таблиц управляют миграции.

**Исходная база ПР7** — `data/craftbox.sqlite`. Она сохранена и используется
только как источник переноса. Резервная копия — `data/craftbox_backup.sqlite`
(не включается в Git). **Консольная версия** продолжает работать с JSON в `data/`.
Консоль и сайт автоматически друг с другом не синхронизируются.

Для первоначального переноса после применения миграций:

```powershell
python db/inspect_source_db.py
python db/import_sqlite_to_orm.py
```

Скрипт читает исходную базу в режиме только чтения и записывает данные через
`update_or_create()` внутри `transaction.atomic()`. Сохраняются ID, остатки,
даты, связи и признаки отмены. Перенос не применяет операции к остаткам повторно.
Повторный запуск обновит совпадающие ID данными из ПР7, поэтому не запускайте
его ради обычного просмотра сайта после изменения данных через ORM.
Посторонние записи целевой базы импорт не удаляет.

Если нужно перенести изменения из консоли, сначала обновите исходную базу
прежней командой `python -m db.import_json`, затем выполните перенос в ORM.
Это осознанная перезагрузка исходных значений, а не автоматическая синхронизация.

## Модели Django и связи

- `materials/models.py`: **Material** — `id`, `name` (CharField, 200),
  `category` (CharField, 100), `count` (PositiveIntegerField), `added_at`
  (DateField), `slug` (уникальный SlugField), `is_low_stock` (GeneratedField).
  Признак низкого остатка вычисляется SQLite по условию count <= 3 и не редактируется вручную.
- `operations/models.py`: **User** — `id`, `name` (CharField, 200), `email`
  (EmailField, unique=True). Это пользователь предметной области, не модель входа
  `django.contrib.auth`. Новое приложение не создавалось.
- `operations/models.py`: **Operation** — `id`, `material`, `user`, `amount`
  (IntegerField, ноль запрещён CheckConstraint), `created_at` (DateField),
  `status` (CharField с TextChoices: active, cancelled, completed; по умолчанию active).

Первичные ключи BigAutoField создаются Django. Связи `Operation.material` и
`Operation.user` — ForeignKey с `on_delete=PROTECT` и
`related_name="operations"`. Нельзя удалить материал или пользователя с историей;
обратные связи доступны как `material.operations.all()` и `user.operations.all()`.
Обычное создание операции через `objects.create()` теперь автоматически меняет
остаток. Изменение количества или материала применяет только разницу; отмена
возвращает прежнее влияние, восстановление применяет его заново. Переход между
активным и завершённым состояниями остаток не меняет. Завершённый расход уже
израсходовал материал: его завершение не создаёт новый запас.
Удаление экземпляра и `Operation.objects.filter(...).delete()` также возвращает
влияние операции. При недостаточном остатке действие запрещается. Все эти
изменения атомарны; повторное сохранение не применяет количество второй раз.

Для изменения количества и статуса операций используйте экземпляры с `save()`,
`cancel()` и `restore()` либо Django Admin. `QuerySet.update()`, `bulk_create()` и
`bulk_update()` обходят model.save() и не предназначены для обычных изменений
истории: они используются только при контролируемом переносе снимка ПР7.
Не меняйте остаток вручную второй раз после создания операции.

Миграции ПР10:
- materials/0002 добавляет GeneratedField, slug и подсказку;
- materials/0003 заполняет slug; materials/0004 включает уникальность;
- operations/0002 добавляет status; operations/0003 переносит старые признаки;
- operations/0004 удаляет is_cancelled после перевода прикладного кода и тестов.

Ранее отменённые записи получают cancelled, остальные — active. Completed не
назначается автоматически по дате. Настройка DATABASES не изменена.
Резервная копия базы перед ПР10 — `data/craftbox_pr10_backup.sqlite3` (в Git не входит).

Обычные классы в `models/` сохранены для консольной версии.

## ORM-запросы ПР9

Представления больше не импортируют sqlite3 и не выполняют ручной SQL.
Основные маршруты и оформление сохранены. Карточки материалов используют slug; прежние числовые URL перенаправляют на них. Общая навигация показывает число материалов.
В проекте используются 15 различных выражений получения данных, перечисленных
ниже. Условные фильтры и варианты сортировки входят в соответствующие цепочки
и не считаются отдельными запросами только ради количества.

| № | Выражение и назначение | Где используется |
|---|---|---|
| 1 | Material.order_by: список по названию и ID | materials/views.py, materials |
| 2 | values + distinct: список категорий | material_search |
| 3 | all + filter по категории, остатку и Q с icontains + order_by: поиск материалов | material_search |
| 4 | get_object_or_404(Material, slug=...): один материал | material_detail |
| 5 | material.operations.select_related("user").all(): история | material_detail |
| 6 | Operation.all + active/cancelled/completed/for_date + filter + Q по связанным полям + annotate(F, Case) + values + order_by: список операций | operations/views.py, operations |
| 7 | select_related("material", "user") + get_object_or_404: одна операция | operation_detail |
| 8 | User.order_by: варианты пользователей в форме | operations |
| 9 | aggregate(Count, Sum, Min, Max, Avg): общие итоги | homepage/views.py, statistics |
| 10 | Operation.aggregate(Count с Q по статусам): итоги операций | statistics |
| 11 | filter(count__lte=...).order_by(...)[:5]: низкие остатки | statistics |
| 12 | values("category").annotate(Count, Sum): по категориям | statistics |
| 13 | annotate(Count, Sum с условием Q) + values: активность материалов | statistics |
| 14 | annotate(Count с условием Q) + values: активность пользователей | statistics |
| 15 | values + annotate + filter по агрегату: категории с 2 и более материалами | statistics |

Варианты материалов в форме операций используют то же выражение, что список
материалов, и повторно не учитываются. Кроме этих выборок, перенос использует
update_or_create() для материалов и участников и контролируемую запись истории
без повторного изменения остатков. CRUD проверяется на тестовых данных; для
изменений доступны Django Admin и пользовательские формы операций ПР11.

Статистика включает материалы и пользователей без операций. Показатели активной
истории учитывают только status=active; отдельно показаны общее число операций и
числа всех трёх статусов. Текущие остатки хранят фактическое количество, включая
влияние завершённых операций.

Примеры адресов:

```text
/materials/search/?q=Акварель&category=Краски&max_count=3
/operations/?status=active&material=2&user=1&date=2026-09-28
/operations/?q=Кисть&sort=material&page=1
```

Допустимые `sort`: `date` (по умолчанию, новые сначала), `material`, `user`.
Неизвестная сортировка, неверная дата или отсутствующий объект в поле выбора
показывают ошибки формы и пустую выборку. Сортировка без заданного значения —
по дате. Отсутствующий объект по адресу карточки возвращает 404.
Фильтрация и сортировка выполняются до Paginator; на странице 5 записей.
Тег `{% querystring %}` сохраняет GET-параметры в ссылках пагинации.
`page=abc` открывает первую страницу, слишком большой номер — последнюю.
Поиск использует стандартный `icontains`; SQLite не обеспечивает полноценное
сравнение без учёта регистра для всех символов Unicode, включая кириллицу.

SQL-файлы ПР7 (`sql/schema.sql`, `sql/queries.sql`), `db/database.py` и
`db/import_json.py` сохранены как предыдущая реализация и средство подготовки
источника. Ручной SQL в новых скриптах нужен только для инспекции и чтения старой
базы; запись в новую базу и все представления используют ORM.

в автоматических тестах. Установка выполнена по
[официальной инструкции Django Debug Toolbar](https://django-debug-toolbar.readthedocs.io/en/stable/installation.html).

## Административная панель ПР10

Создайте рабочую учётную запись (пароль вводится в терминале и не хранится в коде):

```powershell
python manage.py createsuperuser
python manage.py runserver
```

Откройте `http://127.0.0.1:8000/admin/`. Встроенный пользователь Django для входа
и `operations.User` для истории — разные модели.

В `materials/admin.py` настроены столбцы, редактирование остатка из списка,
поиск по названию и категории, фильтры по категории и низкому запасу, сортировка,
по 20 строк на странице, аннотация числа активных операций и ссылка на сайт.
В карточке материала показана история через TabularInline без добавления и удаления.

В `operations/admin.py` зарегистрированы User и Operation. Для операций доступны
поиск по материалу/участнику, фильтры по дате и статусу, навигация по датам,
автодополнение связанных объектов, список с list_select_related и массовые
действия отмены, восстановления и удаления. Inline в карточке участника показывает
его операции. Ошибки остатков и целостности при сохранении выводятся сообщением;
массовая смена статусов откатывается целиком при ошибке.

Группа для проверки прав в автоматических тестах имеет view/add/change материала
без delete; она не является суперпользователем. Проверка выполняется в тестовой
базе и не создаёт дополнительных рабочих учётных записей или групп.

`materials/context_processors.py` передаёт site_name и site_materials_count в общие
шаблоны. Это один дополнительный COUNT на страницу, где используется общий шаблон.
Метод `Material.get_absolute_url()` формирует адрес через reverse. Slug создаётся
транслитерацией Unidecode с добавлением ID и сохраняется при переименовании.

Анализ SQL публичных страниц без входа и без учёта служебных запросов панели:
список операций без заполненных фильтров — 5 запросов (COUNT пагинации, COUNT навигации, два справочника,
выборка страницы с JOIN и LIMIT/OFFSET); карточка операции — 2 (запись со связями
и COUNT навигации); статистика — 8. Авторизация и сама админка добавляют свои
служебные запросы. Проверка списка админки подтверждает отсутствие N+1 при росте
числа строк; добавлять prefetch_related() к values() не требуется.

В ПР11 заполненный ModelChoiceField дополнительно проверяет выбранный ID
запросом к базе: выбор материала и пользователя добавляет два запроса.

## Пользовательские формы ПР11

Классы расположены в `operations/forms.py`, новое приложение не создавалось.
`OperationFilterForm` наследует `forms.Form` и проверяет прежние GET-параметры:
`q`, `date`, `material`, `user`, `status`, `sort`. Дата становится объектом date,
материал и участник — существующими объектами моделей. Неверные параметры
показывают ошибки и не применяются к выборке. Менеджер статусов, аннотации,
values(), порядок сортировки, 5 строк на странице и querystring сохранены.
История по умолчанию по-прежнему показывает все статусы.

`OperationForm` наследует `ModelForm` и разрешает только `material`, `user`,
`amount`, `created_at`. Поля ID и status пользователю недоступны; новая операция
получает статус active из модели. Положительное количество пополняет запас,
отрицательное расходует его, ноль не разрешён. Участник истории выбирается
из `operations.User`, а не из учётных записей Django Admin.

Маршруты в существующем пространстве `operations`:

- `/operations/create/` (`create`) — GET показывает форму, POST создаёт запись;
- `/operations/<id>/edit/` (`update`) — та же форма с instance обновляет запись;
- `/operations/<id>/cancel/` (`cancel`) — только POST меняет статус на cancelled.

После успешного POST выполняется перенаправление к истории. Ошибки и введённые
значения остаются в форме. Все изменяющие формы содержат CSRF-токен; GET к отмене
возвращает 405. Отсутствующие и неактивные записи при редактировании или отмене
возвращают 404. Отменённые и завершённые операции доступны для просмотра;
для административных действий остаётся админка.

Новая дата не может быть раньше текущей даты по часовому поясу Django.
При редактировании старой операции разрешено оставить исходную дату,
но нельзя подставить другую прошедшую дату. Это правило относится к новой
пользовательской форме; прежняя история и админка автоматически не меняются.

ModelForm вызывает проверку модели: остаток рассчитывается с учётом прежнего
влияния редактируемой операции. Сохранение без изменений не списывает запас
повторно. Метод save() модели повторяет проверку при записи и атомарно меняет
историю и остаток. Отмена расхода возвращает запас; отмена пополнения запрещена,
если его количество уже израсходовано и получился бы отрицательный остаток.
Ошибки бизнес-правил и целостности обрабатываются без показа внутренней ошибки БД.

Загрузка изображений в ПР11 не включена: в итоговом разделе методички она
дополнительная, а для материалов выбрана основная часть с формами.
Модели, таблицы и миграции в ПР11 не менялись; новые зависимости не требуются.
Проверки форм находятся в `tests/test_forms.py`; полный набор — 151 тест.

## Изменения к примерам защиты ПР9

- Вместо `is_cancelled=False` в ORM используйте `Operation.objects.active()` или
  `status=Operation.Status.ACTIVE`; для отменённых и завершённых есть свои методы.
- В примерах Q по обратной связи используйте `operations__status`.
- Operation.objects.create() теперь само меняет остаток; второй ручной пересчёт
  не нужен. Это согласованное изменение поведения в ПР10.
- Карточка материала открывается через get_absolute_url() и slug, старый ID-адрес
  делает перенаправление; методы get(pk=...) в Django shell продолжают работать.
- is_low_stock у ORM Material теперь поле, а не вызываемый метод.
- Общие данные из контекстного процессора добавляют запрос COUNT, поэтому один
  JOIN для карточки не означает один SQL-запрос всей страницы.

## Что где лежит

Проект разложен по смыслу, и каждая часть занимается своим делом.

**Настройки сайта** лежат в папке `craftbox/`: там общие параметры и главная «карта» адресов, которая решает, какому разделу отдать запрос.

**Общие шаблоны** — папка `templates/` рядом с `manage.py`: каркас всех страниц и меню.

**Три раздела сайта** — папки `homepage/`, `materials/` и `operations/`. В каждой свои адреса, функции, которые готовят данные, и папка `templates/` со своими страницами. Внутри неё есть ещё одна папка с именем раздела, чтобы одинаковые имена файлов в разных разделах не путались. У главного раздела есть ещё папка `static/` — там стили, картинка и скрипт. Для пользователей отдельного раздела нет: в Django уже есть встроенные пользователи, и ими займёмся, когда дойдём до входа на сайт.

**База данных** — `db.sqlite3` для ORM; модели и миграции в приложениях, скрипты инспекции и переноса в `db/`. В `data/` сохранена исходная база ПР7, в `sql/` — её схема и прежние запросы.

**Классы предметной области** — папка `models/`: здесь описано, что такое материал, пользователь и операция и что с ними можно делать. Ими пользуется консольная версия.

**Консольная версия, хранение и ввод данных** — отдельные файлы в корне проекта. Они остались с прошлых этапов и продолжают работать.

**Папка `data/`** — ваши данные. **Папка `tests/`** — автоматические проверки, теперь в том числе для страниц сайта.

Остальное — служебные файлы с настройками и списком зависимостей.

## Как запустить

Нужен Python 3.10 или новее.

```
python -m venv venv
venv\Scripts\activate          # Windows
source venv/bin/activate       # macOS и Linux
pip install -r requirements.txt
python manage.py migrate
python db/import_sqlite_to_orm.py  # перенести данные из базы ПР7 в ORM
python manage.py runserver
```

После этого откройте в браузере http://127.0.0.1:8000/

Консольная версия запускается как раньше:

```
python main.py
```

## Если вы разработчик

```
pytest -v                                           # тесты: классы, данные и страницы сайта
flake8 . --extend-exclude=venv                      # проверка оформления кода
python manage.py check                              # проверка настроек Django
python manage.py findstatic homepage/img/logo.png   # находит ли Django статику
sqlite3 data/craftbox.sqlite                        # открыть базу и выполнять запросы вручную
```

Тесты не трогают рабочие базы: исходная база для теста собирается из JSON во временном каталоге, ORM работает с отдельной тестовой базой Django в памяти. Проверяются также CRUD, связи, ограничения, перенос, отмена, поиск, фильтры, пагинация и статистика.

Используются Python, Django 5.2 и его язык шаблонов, SQLite и Django ORM, Django Debug Toolbar, Unidecode, HTML, CSS, JavaScript, Bootstrap 5.3, JSON, pytest и flake8.
